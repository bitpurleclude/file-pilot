# 治理层核心机制设计

版本：v1.1（2026-10-11）
状态：设计草案（机制与概念定义；表结构与 API 细节待实施阶段的技术评审定稿）
前置阅读：`vision.md`（原则）、`domain-research.md`（蓝图来源）

## 0. 与现有架构的关系

治理层**不替换**现有管线，而是在其上游与外围扩展：

```
现状：拖拽 → analyze（规则→LLM→兜底）→ plan（即兴路径）→ apply/dry-run → rollback
目标：Inbox/拖拽 → 【登记册路由 → 规则命中 → LLM 认领坐标 → 兜底】→ plan（登记册坐标）
        → apply/dry-run → rollback
       另有：建域向导 / 周报 / lint / 逻辑视图 / 溯源查询（均为治理层新增面）
```

复用清单：sessions + rollback（重排执行器）、规则引擎（路由第一级）、批式 LLM 链路（模糊路由）、SQLite + 迁移机制（登记册存储）、e2e 基建（llm-stub 可模拟「坐标清单注入」后的行为）。

## 1. 登记册（Registry）

### 1.1 概念模型

采用 Johnny.Decimal 分区法的两级坐标：

- **领域（Area）**：人生板块，编号 `10-80`（十进制槽位，预留空号；`90` 起保留给归档/暂存容器），如 `10-开发`、`30-考公`。数量恒少（个人 ≤8，恰好对应 8 个槽位）。
- **项目（Project）**：领域内生灭频繁的单元，编号 `x1..x9`（单域 9 个槽位，显示为 `1-行测`），如 `30-考公/1-行测`。**不需要预留**——项目按需认领本域下一个空号，全局数量不设上限；单域槽位用尽时新开领域扩容。

坐标表示：`<area编号>-<领域名>/<项目编号>-<项目名>`，如 `30-考公/1-行测`。坐标是全系统唯一的「去处」表达：落位路径、规则条件、LLM 提示词选项、周报统计全部使用坐标。

### 1.2 存储草案（SQLite，走现有迁移机制）

```
areas:      id, number(10..80), name, status(active|archived), created_at, retired_at
projects:   id, area_id, number(1..9), name, aliases(keywords), status, created_at, retired_at,
            sample_paths（创建/修正时积累的样本文件路径，供查重与规则学习）
```

约束：area.number / project.number 唯一；坐标占用即查重依据；`status` 支撑退役协议。现有 `classification_rules` 增加 `project_id` 外键（替代自由字符串 project）。

### 1.3 初始化

首次使用提供两种起点：空白（仅 `00-Inbox` + `90-Archive` + `99-Temp` 三个保留容器）；或从现有盘扫描结果半自动导入（见 roadmap 阶段④）。

## 2. 出生协议（建域向导）

触发：用户声明新领域/项目，或周报中重复主题达到阈值时半自动提议。

流程（人工决策只发生在最后一步）：

1. 用户输入候选名称；
2. 工具执行**三级查重**：a) 坐标占用检查（编号/名称精确）；b) 名称语义相似度（含别名）；c) 内容抽样比对（候选域样本文件 vs 既有域 sample_paths，LLM 参与判定）。c 的算法选型见 `research-notes.md` §5：名称精确/编辑距离 → MinHash/SimHash 指纹 → LLM 语义判定三级漏斗；
3. 命中 → 呈现证据（「已有 `30-考公`，含 14 个样本与之相似」）→ 用户选择**并入**（挂到既有域）或**仍新建**（记录决策理由）；
4. 未命中 → 认领下一个空号，登记完成。

设计依据：用户痛点「忘记建过类似的」的软件化解法 = **在出生时刻强制回看历史**，而非依赖记忆。

## 3. 退役协议

- **项目完结**：整目录原子搬入 `90-Archive/<area>/<project>`（保留完整层级上下文），status → archived，全程一个可回滚会话。
- **领域完结**：域下全部项目连带搬入 `90-Archive`，编号空出**不复用**（新领域取新空号，避免历史坐标歧义）。
- 退役不删除、不拆散：找回时按「归档区 + 原坐标」确定位。

## 4. Inbox 自动处理管线

### 4.1 管线

```
新文件进入 00-Inbox
  → 1) 命名/来源规则（确定性：下载器目录、安装包归档、程序排除区）
  → 2) 登记册坐标规则（源目录在项目槽下 → 直接归入）
  → 3) LLM 认领（提示词注入当前坐标清单；置信度 ≥ 高阈值 → 自动入位 +「未确认」标记）
  → 4) 寄存（置信度 < 阈值 → 留在 Inbox 的「待定」区，不逼问，攒上下文）
  → 5) 周报（待定项 + 未确认项聚合成一次性批量确认界面）
```

### 4.2 关键规则

- **程序排除区**：已安装软件、被路径引用的目录（如 `D:\tool` 类）永不搬迁；工具维护排除清单；移动目标若为 exe 所在目录 → 硬拒绝。安装包（文件）与已安装程序（路径依赖）分开处理。
- **Inbox 衰老**：待定项超期（默认 30 天）→ 按「最佳猜测」自动入位并保留未确认标记（错而可寻 > 乱而不见）。
- **预算指标**：周报统计「人工决策/文件」比值，产品目标 ≤ 0.1。

### 4.3 LLM 提示词改造要点

- 批式模板注入当前领域+项目坐标清单；指令：project 字段**只能从清单认领**，确需新建则输出 `NEW:` 前缀（触发建域向导而非直接落盘）；
- 同批文件明显同源时必须复用同一坐标；
- project 输出做**枚举校验**（必须命中清单或带 NEW 前缀）——这是「模型从编名字变认坐标」的机械保证。

### 4.4 决策模型层（本地优先）

2026-09 起出现"System One 决策模型"品类（Jev 闭源 / **Laya** Apache 2.0 开源可本地部署 / Nimble，对比与选型详见 `decision-models.md`）。此类模型只做类型化判断（Choice/Score/Null），与本项目 LLM 工作负载（坐标认领、置信打分、查重判定）完全对口，且本地部署使文件数据永不出机、消除 API Key 依赖。

接入设计：

1. **两级分解决策**（硬约束）：坐标认领分解为先领域（≤8 选项）后项目（≤9 选项，单域槽位上限）——决策模型在选项 >20 时精度崩塌（Laya 独立评测数据），两级分解恰好落入其能力包络（≤10），且与登记册两级结构天然对应（学术依据：层级分类的 local 方法，`research-notes.md` §4）。
2. **管线角色**：`规则 → 本地决策模型（中间层）→ 云端 LLM（疑难升级：NEW:/低置信/跨域）→ 本地兜底`。本地模型位置在 Inbox 后台批处理（CPU 时延 193–464ms，不适合拖拽即时交互）。
3. **Null 原语 → 寄存区**：以 Null（校准 P(true)）显式提问「能否自动入位」，低概率与低置信 Score 一并进寄存区——显式否决比阈值切分更可靠。
4. **微调飞轮**：周报改判/手工修正积累带坐标标注样本 → SetFit 对比微调（几十条起效）→ Laya 微调 → 达标后接管中间层（采纳路径与硬指标见 `decision-models.md` §5）。
5. **校准纪律**：任何接入模型的原始置信度不可直接当分流阈值，须过校准检查（可靠性图/ECE），必要时温度缩放（`research-notes.md` §6）；分流阈值的中期升级方向是共形预测弃权（分布无关错误率保证，免训练，`research-notes.md` §1）。

## 5. 命名 lint

规则集来源：r/datacurator 社区规范。初版规则：

1. 目录/文件名禁 Windows 非法字符（沿用现有 `sanitizePathSegment` 白名单逻辑）；
2. 日期一律 ISO 8601 前缀（`2026-10-06`）；
3. 版本用 `v01/v02`，文件名出现 `final/final2/最终版` → 告警；
4. 建议无空格（点或连字符分隔）；
5. 重复坐标/近似名称（`video` vs `vedio`）在登记册内不允许产生（出生协议已挡），对登记册外目录由全盘扫描报告覆盖。

lint 是**告警不阻塞**：出现在周报中，由用户决定是否修（修复动作走可回滚会话）。

## 6. 逻辑视图（交叉的答案）

需求：一个文件逻辑上属于多处（如「所有 2026 年的 PDF」跨领域）。

- **语义**：对齐 DEVONthink Replicate——文件物理仅一份，视图成员是引用；视图由规则（坐标/标签/日期/名称模式）动态定义或手动圈选。
- **实现选型（留待技术评审）**：a) NTFS junction/symlink（资源管理器原生可见，但有循环与同步工具风险）；b) 纯索引视图（工具内渲染，零文件系统副作用，推荐首版）；c) .lnk 快捷方式批量生成（兼容性最好，体验最差）。
- 硬约束：视图永不产生第二份字节。

## 7. 溯源查询（文件去哪了）

- 数据源：现有 `sessions.executions_json`（已含每次搬移的源/目标路径）与 `session_items`（源路径）；单条搬移的精确时间目前只有会话级时间戳，实施时补充 per-move 时间（或经 `logs_index` 关联）。
- 形态：输入路径或文件名片段 → 返回该文件的移动链（原位置 → 历次目标 → 当前位置），含会话号与时间。
- 这是「北极星指标 1（找得回）」的直接兑现，基本无新增存储（搬移源/目标已在落库，仅需补单条时间戳）。

## 8. 批量重排引擎（层级修订）

- 任何结构性修订（合并目录、重命名域、退役归档）编译为一批 plan → 走现有 apply/rollback 执行器；
- 会话类型标记 `restructure`，周报与溯源查询可按类型过滤；
- 安全边界：程序排除区硬拒绝；白名单校验沿用；单 plan 失败不阻断批次（现有执行器行为）。

## 9. 度量

| 指标 | 定义 | 目标 |
| --- | --- | --- |
| 人力决策率 | 周报内人工决策数 / 处理文件数 | ≤ 0.1 |
| 自动入位准确率 | 未确认项中经用户改判的比例（抽样） | ≥ 90% |
| 溯源覆盖率 | 工具经手文件可回答「去哪了」的比例 | 100% |
| 规则命中率 | 走规则路径（0 LLM 成本）的文件占比 | 持续上升 |
